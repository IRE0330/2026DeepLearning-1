# 향후 예측모델 연결 위치와 데이터 계약

현재는 집계와 CSV 저장만 수행합니다. 예측모델 호출·전송·구독기·전송 이력 DB는 구현하거나 실행하지 않았습니다. 아래 소비·중복 방지 절차는 향후 연결 설계입니다. 사용자 가정의 `expected_wait_s`는 기존 계산식의 값이며 예측모델 출력이 아닙니다.

## 현재 분리된 처리

1. `Counter.update()`가 모든 처리 프레임의 탐지·추적 결과로 출입/대기 상태와 누적 인원을 계산합니다. 기록 간격을 바꿔도 탐지·추적·판정 주기는 그대로입니다.
2. `IntervalSampler.push()`/`finish()`가 설정된 영상 시각 경계에서 `row, detail`을 생성합니다. 첫 구간은 시작 포함, 이후 구간은 이전 경계 초과·현재 경계 이하입니다. `usage_row()`가 공유13열과 계산값을 구성합니다.
3. `IntervalCSVWriter.write()`가 영상별 CSV에 행을 추가하고 flush한 뒤 상세 JSONL도 저장·flush합니다. `pipeline.persist_interval()`은 저장이 끝난 후에만 선택적 `interval_sink(row, detail)`을 호출합니다.
4. 현재 batch의 `interval_sink`는 `DailyCSVWriter.add()`입니다. 해당 화장실/날짜의 행 목록에 추가하고 정렬한 새 파일을 임시 `.csv.tmp`에 저장·flush·fsync한 뒤 원자적으로 교체합니다. 기존 파일을 읽던 소비자는 이전 완성본, 새로 여는 소비자는 다음 완성본을 읽습니다.

향후 모델 어댑터는 `Counter`/`IntervalSampler`/CSV writer에 넣지 않고 별도 소비 모듈로 둡니다. 연결 지점은 영상별 저장 후의 sink, 또는 batch 날짜 파일의 저장 완료 후입니다. 원격 호출이 프레임 처리를 막지 않도록 향후 별도 소비 작업/저장된 레코드 큐를 고려합니다. 현재 sink에는 모델 함수를 연결하지 않았습니다.

## 전달할 데이터 구조

현재 생성되는 원본 레코드는 `row`(정확한 공유13열)와 `detail`(아래 구조)입니다. `interval_details.jsonl`에도 같은 상세 값을 저장합니다.

| 필드 | 형식과 의미 |
|---|---|
| `restroom_id`, `video_id` | 환경 ID와 원본 영상 ID |
| `record_index` | 해당 영상 분석 시작 이후 생성한1번째,2번째… 기록 번호 |
| `record_interval_s` | MVP1초/운영10초 등 실제 적용한 간격 |
| `interval_start_s`, `interval_end_s` | 원본 영상 기준 기록 구간 경계 |
| `source_time_s` | 경계 이하에서 사용한 가장 최근 프레임의 원본 시각 |
| `interval_entries`, `interval_exits` | 해당 구간의 확정 출입 수 |
| `state` | 해당 소스 프레임의 누적출입·내부원시인원·candidate/confirmed/유예·외부대기·내부추정대기·현재대기/Q·빈칸추정·사용자 예상시간·관측상태 |
| `available_stalls`, `average_stall_use_s` | 저장 상세에 추가하는 운영 총칸 수·평균 이용시간 가정 |

향후 어댑터의 전달 묶음에는 위 `row, detail`과 함께 실행 식별자(고유 실행 폴더), `config_used.json`의 `profile_name`, 가상/실제 촬영시각 구분, 대기 집계 정책과 영상 SHA-256을 포함합니다. 시연 가정과 관측 불확실성은 `row['측정상태']`를 그대로 전달합니다. `state.measurement_status`만 사용하면 시연 가정 표기를 놓칠 수 있습니다. 알려지지 않은 값은 null로 유지하며 빈칸을0으로 바꾸지 않습니다. 현재/전체대기는 같은 Q이고, 내부대기를 다시 더하지 않습니다. baseline이나 미검증 상태를 정확도 검증 자료로 취급하지 않습니다.

실행 식별자+화장실ID+영상ID+`record_index`의 튜플을 레코드 고유키로 설계합니다. 값이 같은 연속 초도 각각 다른 기록입니다. 모든 필드의 값이 같다는 이유로 한 행을 버리지 않습니다. 실행 설정을 바꾼 재실행은 새 실행으로 구분하며, 소비 대상 실행을 명시적으로 선택합니다.

## CSV를 읽을 때의 완성 행과 중복 방지 설계

- 날짜별 공유 CSV를 우선 소비합니다. `.csv.tmp`는 읽지 않고 공개된 `.csv` 완성본만 엽니다. 단일 영상 `usage_summary.csv`를 직접 읽으면 UTF-8 디코딩, 마지막 레코드의 줄 종결, 따옴표를 포함한 strict CSV 파싱, 정확한13열을 모두 확인합니다. 저장 중 잘린 끝 행/다중행 문자열은 다음 읽기까지 보류하며 임의로 빈 값을 채우지 않습니다.
- 날짜 파일은 정렬 후 전체 교체될 수 있으므로 파일 바이트 오프셋·mtime·전체 행 번호를 처리 완료 기준으로 사용하지 않습니다. 완성본을 다시 읽고 고유키로 새 행을 구분합니다. 다른 영상의 앞선 시각 기록이 중간에 삽입돼도 처리 이력이 유지돼야 합니다.
- CSV의 촬영시각이 있으면 고유 실행 폴더+화장실ID+영상ID+구간 시작/종료시각으로 키를 구성할 수 있습니다. 자정 파일이 바뀌어도 같은 키 기준을 유지합니다. 촬영시각이 비어 있으면 CSV만으로 동일한 값의 연속 초를 구별할 수 없습니다. 이때 `interval_details.jsonl`의 영상ID/`record_index`/원본 경계를 함께 쓰거나, CSV 단독 전달을 보류합니다. 행 내용 해시만으로 중복을 판단하지 않습니다.
- 향후 처리 이력 저장소에는 고유키에 UNIQUE 제약을 두고 pending/acknowledged 상태를 영속 저장합니다. 이미 접수 완료된 키는 다시 전송하지 않고 프로그램 재시작 후에도 이력을 복구합니다. 같은 원본 행의 재시도는 같은 키를 사용합니다.
- 네트워크에서 수신 후 응답이 유실되면 재시도가 생길 수 있으므로 향후 수신 모델 서비스도 고유키를 확인하고 중복을 멱등 처리해야 합니다. 로컬 기록만으로 네트워크의 정확히 한 번 전달을 보장한다고 주장하지 않습니다.

위 소비/전송 설계는 현재 실행되지 않습니다. 오늘 생성된 CSV와 상세 레코드는 추후 어댑터가 사용할 수 있는 저장 자료입니다.
